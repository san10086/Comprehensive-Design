## 2.3 进程生命周期与错误处理

### 页面内容

**GUI 保持响应，分阶段管理 DSP 启动、host 运行和 DSP 卸载。**

```text
配置与文件校验 → 加载 DSP → 运行 app_host → 卸载 DSP → 回收任务
```

| 问题或触发条件 | 已实现处理 |
|---|---|
| 文件缺失、权限错误、方向无效 | 启动前检查，显示具体错误并保留日志 |
| loader 启动失败 | 不进入 host 阶段，标记 DSP 状态待检查 |
| host 失败或退出 | 进入卸载阶段，保留退出码；异常任务限制再次启动 |
| 用户点击停止或关闭窗口 | 等待 `main: control ready`，向当前 host 发送 SIGINT，退出后卸载 DSP |
| GUI 重复启动、阶段或停止等待超时 | 本地文件锁防止重入；加载/卸载及停止等待 30 秒后提示，保留界面和日志 |

**已修正的回归问题：QProcess 启动失败后，延后到下一次事件循环执行清理，避免同一对象立即重用引起重入。**

```sh
# 板端各阶段的等价命令；GUI 会按状态依次执行
./slaveloader startup DSP server_dsp.xe674
./app_host DSP smoke --algo passthrough
./slaveloader shutdown DSP
```

### 汇报讲稿

界面能够启动进程只是第一步，真正需要处理的是失败与退出顺序。这里把流程做成分阶段状态控制：加载失败不进入业务，host 退出后执行卸载，停止时等待 host 安装好信号处理再发送 SIGINT。测试还发现启动失败回调中立即复用 QProcess 的重入问题，已改为在下一次事件循环继续清理。桌面环境的生命周期与 IPC QtTest 汇总为十五项通过，但真实板端业务仍需按相同阶段验收。

制作备注：

- `record` 只启动录音 host，不加载 DSP，上述三阶段示例针对使用 DSP 的模式。
- 任务锁位于 `/tmp/ex04-qt-audio.lock`，协调 GUI 实例，不会阻止其他终端手工启动 host 或 `run.sh`。
- 30 秒提示用于 loader 阶段及请求停止后的等待，不是正常运行期间 host 的通用无进展监测，也不是强制停止时间保证。ALSA/驱动阻塞时需保留现场；不将强杀 loader/host 作为正常停止流程。
- IPC 示例辅助进程有独立的超时结束策略，与持有音频/DSP 资源的 host 生命周期不同。
- 不并发手动执行示例命令与 GUI 音频任务。首次板端分阶段验证应沿用已核对的固件与内存配置。

依据：[E01]、[E04]、[E06]。

## 2.4 IPC：独立 C 进程与 Qt 的同步、数据交互

### 页面内容

**实现两类 Linux System V IPC 验证：信号量握手、共享内存数据交换。**

```text
C peer：等待可写 → 写入序号与数据 → 置可读
Qt 线程：取得可读 → 复制内容、校验序号 → 置可写 → 信号更新界面
```

- 每次会话完成 **10 条消息**，通过序号和握手避免覆盖；测试进一步核对消息内容。
- GUI 使用工作线程读取，非阻塞轮询信号量，界面线程负责绘制和交互。
- Qt 创建并管理会话资源，结束时回收线程、子进程、信号量和共享内存。
- 已覆盖正常完成、提前停止、异常退出和资源移除；桌面 QtTest 使用的 IPC 为真实 Linux 内核资源。

```sh
# Ubuntu 开发机，在工程根目录；已完成本机架构 build-desktop 构建
EX04_IPC_PEER="$PROJECT_ROOT/frontend_arm/build-desktop/bin/ex04_ipc_peer" \
  python3 frontend_arm/tests/test_ipc_peer.py
```

**界面操作：诊断 → 信号量 / 共享内存 → 观察 1–10 条交互 → 再运行或停止验证。**

### 汇报讲稿

课程要求的进程交互采用独立 C 进程和 Qt 接收线程实现。两个信号量控制可写与可读，写入序号和内容后再通知，Qt 复制完成后才允许下一次写入。这样既能验证同步，也能发现丢消息或覆盖。桌面测试使用真实 System V IPC，并检查停止和异常后的回收。该示例已经建立进程间交互基础，但目前尚未承载 app_host 的真实实时 PCM。

制作备注：

- 上述测试命令需先 `source /home/user/ex04-build-paths.sh` 并在工程根目录执行。桌面测试使用本机架构的 peer，ARM 交叉编译产物放到 ARM 环境运行。
- 资源由 `IPC_PRIVATE` 创建，权限 0600，semid/shmid 写入日志。外部强杀或断电后的残留只按该会话 ID 定向核对、清理。
- System V 共享内存用于 Linux 进程间通信，TI SysLink 的 SharedRegion 用于 ARM/DSP，二者分开验证。
- 历史 C IPC 集成测试为 6 项通过；本次桌面 Qt 生命周期及 IPC 的汇总为 15 passed，包括初始化/清理项，不相加宣称为互不重叠的“21 项独立功能”。
- 如需补板端 IPC 证据，应在 ARM GUI 中操作两项验证，记录 `IPC_RECEIVED sequence=1..10` 与资源清理结果。当前材料不能替代该板端验收。

## 3.2 RPE 引入准备与技术路线

### 页面内容

| 准备任务 | 拟完成的工作 | 阶段验收 |
|---|---|---|
| SDK 与例程核对 | 确认 EZSDK 对应的 RPE 库、头文件、固件及课程参考例程 | 原始例程可构建，依赖与内存要求清楚 |
| 最小调用链 | 从课程标准例程开始，实现 ARM 调用 DSP 基础算法 | 固定输入与期望输出一致，错误与退出可观测 |
| 空间算法封装 | 梳理采样率、帧长、方向、输入输出缓冲及跨块状态 | 固定方向卷积与现有参考结果一致 |
| GUI 后端适配 | 保持 GUI 与绘图接口，新增 RPE 调用适配层 | 可通过界面启动、停止并显示状态与结果 |

**拟议结构：Qt GUI → 音频后端适配 → RPE 调用 → DSP 空间算法。**
